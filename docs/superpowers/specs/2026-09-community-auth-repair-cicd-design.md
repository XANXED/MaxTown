# MaxTown: CI/CD, авторизация, сообщество и режим ремонта

## Цель

Подготовить MaxTown к повторяемому развёртыванию на VPS и добавить работающие
серверные функции: вход жильца через MAX, доступ к данным его Дома, общедомовое
сообщество с сообщениями и опросами, а также состояние режима ремонта.

Пользователь выбрал Docker Compose на VPS. В checkout пока нет БД, CI workflow,
production-конфигурации или адреса VPS. Git remote настроен на
`XANXED/MaxTown`, но локальный `gh` не авторизован, а GitHub-коннектор сейчас
возвращает 404. Эти ограничения блокируют публикацию и настоящий deployment,
но не локальную разработку и подготовку CI/CD.

## Текущее состояние и ограничения

- `apps/api` — Fastify-сервер только с `/health`.
- `apps/miniapp` и `apps/admin` показывают локальные fixture-данные; production
  запросы к API для существующих экранов не реализованы.
- `apps/bot` запускает приветствие по `BOT_TOKEN`.
- `packages/shared` уже содержит типы Дома, ролей через текстовые значения,
  Приглашений и Событий.
- ADR-0001 фиксирует роли УК внутри Дома, а ADR-0002 — работу домовых ролей в
  мини-приложении и использование `apps/admin` только Модератором.
- Существующий onboarding предусматривает вступление по приглашению либо
  Запросом на вступление. Приглашение делает человека Жильцом Квартиры.
- Термины и границы сущностей должны соответствовать `CONTEXT.md`. Нельзя
  называть комментарии к Заявке «чатом» или представлять Модератора домовой
  Ролью.

## Принятый дизайн

### Хранилище и API

- PostgreSQL — основное постоянное хранилище; для приложения API использовать
  `pg` с параметризованными запросами и SQL-миграциями. Схема не должна
  зависеть от демонстрационных fixtures.
- Fastify остаётся единственным владельцем проверки MAX `initData`, сессий и
  домовой авторизации.
- Запросы к сообществу и режиму ремонта получают `houseId` только из проверенной
  сессии и membership. Переданный клиентом `houseId` не даёт полномочий.
- Не вводить отдельную сущность управляющей организации; роли сотрудников
  остаются в пределах Дома согласно ADR-0001.

### Вход и сессия

1. Mini App передаёт серверу исходную строку `window.WebApp.initData`.
2. API проверяет уникальность параметров, HMAC-SHA256 подпись, наличие
   пользователя, формат и свежесть `auth_date` по официальной документации MAX.
   Секрет берётся только из `BOT_TOKEN`; клиентские `initDataUnsafe` не
   участвуют в проверке. MAX рекомендует интервал свежести `auth_date` до часа;
   детали проверки: [валидация MAX WebAppData](https://dev.max.ru/docs/webapps/validation)
   и [MAX Bridge initData](https://dev.max.ru/docs/webapps/bridge).
3. После успешной проверки API создаёт или обновляет внутреннего Жильца и
   выдаёт криптографически случайный непрозрачный bearer-токен. В PostgreSQL
   хранится только хеш токена, срок действия ограничен, сервер поддерживает
   logout/revoke. Клиент держит токен только в памяти приложения, не в
   `localStorage`.
4. Роли берутся из связей Жильца с Домом. Роли `Староста`, `Ответственный`,
   `Консьерж` и `Жилец` имеют доменную семантику из `CONTEXT.md`; роль
   `Модератор` остаётся отдельной и не выдаётся через membership.
5. Продуктивная среда не принимает фиктивную авторизацию. Если нужен dev-login,
   он включается отдельным явным флагом, недоступным в production.

### Привязка к Дому

- Существующий invite-flow подключить к постоянному хранилищу: Староста
  создаёт/перевыпускает Приглашение, старый код отзывается; код хранится в БД
  только как хеш.
- После авторизации приглашённый Жилец становится участником указанной
  Квартиры. Проверка и создание membership выполняются одной транзакцией.
- Запрос на вступление без Приглашения остаётся отдельным pending-сценарием,
  который решает Жилец соответствующей Квартиры, либо Староста для пустой
  Квартиры согласно `CONTEXT.md`.
- Подключить существующую регистрацию Дома и очередь `apps/admin` к API:
  Староста создаёт регистрацию после MAX-входа; Модератор одобряет её или
  отклоняет с причиной; одобрение создаёт Дом и membership Старосты.
- Защитить веб-панель и все `/api/moderator/*` на Caddy HTTP Basic Auth с
  индивидуальными логинами и заранее хешированными паролями из deployment
  secrets. API не публикуется напрямую наружу; principal для аудита берётся из
  перезаписываемого доверенным Caddy заголовка. Не помещать credentials в
  Vite bundle. Проверить актуальный синтаксис Caddy до реализации.

### Сообщество и опросы

- Сообщество — одно пространство сообщений на Дом. История постраничная,
  сортируется по времени и ограничивается membership. Пользовательский текст
  хранится как обычный текст и безопасно отображается React без HTML.
- Для первой версии использовать обычные API-запросы и периодическое обновление
  списка сообщений; не добавлять WebSocket-инфраструктуру без необходимости.
- Опрос создают Староста или Ответственный. Опрос содержит вопрос, варианты,
  время закрытия и автора. Один Жилец может один раз проголосовать в каждом
  опросе; после отправки изменить голос нельзя. Сервер защищает это уникальным
  ограничением по опросу и membership. В UI показываются агрегированные результаты.
- Опрос — неофициальный сбор мнений и не является юридически значимым общим
  собранием собственников, кворумом или решением в смысле законодательства.

### Режим ремонта

- У каждого Дома одно текущее состояние: выключен или активен. Активное
  состояние включает заголовок, описание работ, время начала, ожидаемое
  завершение и инструкцию Жильцам.
- Смотреть режим могут участники Дома. Включать, редактировать и завершать его
  могут Староста и Ответственный этого Дома.
- Операции записи сохраняют автора и временные метки. Статус не означает
  подтверждённый внешний статус от УК или подрядчика, если такой интеграции нет.

### CI/CD и Docker Compose

- Первый кодовый этап — GitHub Actions CI: воспроизводимая установка через
  `npm ci`, typecheck, тесты с PostgreSQL service, production build и сборка
  Docker images.
- Deployment pipeline после CI публикует образы в GHCR и разворачивает точные
  digest-образы на VPS через SSH. Использовать GitHub Environment для production
  secrets и approvals, минимальные permissions, закреплённые версии Actions.
- Compose включает PostgreSQL с volume и healthcheck, миграции, API, собранный
  miniapp, admin под защищённым доступом и Caddy для HTTPS/reverse proxy.
  Бот запускается только при наличии его отдельной конфигурации и не должен
  ломать основной сервис, если не используется.
- Обновление БД выполняется до перевода API на новый образ только для
  совместимых миграций. Deployment проверяет `/health` и основные API сценарии;
  при провале возвращает предыдущий image digest, если миграция совместима.
- Secrets, необходимые для реального deployment, включают VPS host/user/SSH
  key, deployment path, домен, `BOT_TOKEN`, пароль/URL PostgreSQL и способ
  защиты admin. Фактические значения не сохраняются в Git.

## Планируемые интерфейсы

Конкретные схемы и имена уточняются перед реализацией, но API должен покрыть:

- `POST /api/auth/max`, `POST /api/auth/logout`, `GET /api/me`;
- регистрацию Дома и moderation endpoints для очереди регистраций;
- проверку/использование Приглашения и Запросы на вступление;
- `GET/POST /api/houses/:houseId/community/messages` с курсором и лимитом;
- `GET/POST /api/houses/:houseId/polls`, голосование и агрегированные итоги;
- `GET/PUT /api/houses/:houseId/repair-mode`;
- защищённые moderator endpoints отдельно от домовых ролей.

Каждый route проверяет authentication, membership и роль. Валидация входных
данных задаётся в Fastify schema; ошибки не включают секреты и SQL.

## Вне объёма первой поставки

- Юридически значимые голосования/ОСС, расчёт кворума и электронная подпись.
- Вложения и загрузка медиа в чате.
- WebSocket push, push-уведомления и отправка сообщений ботом, если это требует
  неподтверждённых правил MAX или отдельного договора.
- Автоматическая интеграция с УК, ГИС ЖКХ, ГАР/ФИАС, DaData или внешними
  сервисами ремонта.
- Редизайн существующих экранов, не связанных с выбранными сценариями.

## Критерии приёмки

- Все защищённые API отказывают при неверной/просроченной MAX-подписи, истёкшей
  сессии, отсутствии membership или недостаточной Роли.
- Житель одного Дома не может читать сообщения, голосовать или менять режим
  ремонта другого Дома подстановкой идентификатора.
- Приглашения и Запросы на вступление устойчивы к гонкам и проверяются на
  сервере; повторно выпущенное Приглашение отзывает прежнее.
- Опрос хранит не более одного действующего голоса на membership и закрывается
  по сроку. Режим ремонта читается всеми участниками и редактируется только
  разрешёнными ролями.
- GitHub Actions запускает typecheck, тесты, миграции, build и Docker build.
- Compose поднимается с чистой БД и проходит health/smoke-check.
- После появления валидного GitHub доступа, VPS, домена и secrets PR/Actions,
  deploy и работающий HTTPS URL подтверждены фактическими результатами.

## Необходимые значения для выкладки

До production deployment владелец должен предоставить или настроить GitHub
авторизацию с правом публикации в `XANXED/MaxTown`, VPS, DNS-домен, SSH deploy
credentials и секреты окружения. Сейчас `gh auth status` сообщает, что токен
невалиден; GitHub API-интеграция не видит репозиторий. До устранения этого
ограничения код, миграции и workflows можно подготовить и проверить локально.
